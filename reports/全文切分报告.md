# PMC oa_comm 全文分块方案报告

> **时间**：2026-06-24  
> **数据集**：PMC oa_comm（CC-BY 商用许可，~527 万篇 JATS XML）  
> **Tokenizer**：`tiktoken cl100k_base`（与 DeepSeek V3/V4、Qwen3 BPE 近似对齐）  
> **嵌入模型 Token 上限**：512

---

## 一、背景与目标

### 1.1 从摘要模式到全文模式

前期工作已完成对 PMC 文献摘要的解析与分块，建立了基础 RAG 检索索引。摘要切分的核心问题在于覆盖率的天花板：摘要平均约 332 tokens，仅能反映研究的高层次概要，对方法细节、数值结果、统计数据等核心内容的检索能力极为有限。

本阶段目标：**将存储与检索单元从摘要扩展至全文正文**，使 RAG 系统能够回答"该研究具体使用了什么统计方法"、"p 值 / 置信区间是多少"等需要正文细节的问题。

### 1.2 全文数据规模

| 指标 | 值 |
|------|-----|
| 全文 Token 中位数 | 12,170 |
| 全文 Token p95 | 31,279 |
| 单章节（`<sec>`）中位数 | 416 tokens |
| 单章节 p90 | 2,003 tokens |
| 段落（`<p>`）超 512 tokens 比率 | **4.8%** |

全文中位数是摘要的 37 倍，直接整体入库不可行。章节层级虽在中位数上接近 512，但 p90 达 2003 tokens，大量章节需要二次切割。段落（`<p>`）层级仅 4.8% 超限，是切分的最优基本单元。

## 二、方法设计

### 2.1 JATS XML 结构利用

PMC 文献采用 JATS XML 格式，结构规整：

```
<article>
  └─ <body>
       └─ <sec>              ← 章节（可嵌套，支持子章节）
            ├─ <title>       ← 章节标题（如 "Methods"、"2.1 Statistical Analysis"）
            ├─ <p>           ← 正文段落
            ├─ <table-wrap>  ← 表格（含 <caption>）
            └─ <fig>         ← 图片（含 <caption>）
```

几乎所有 research-article 均遵循 IMRaD 结构（Introduction / Methods / Results / Discussion），`<sec>` 标签标注层次明确，可直接提取语义边界。

### 2.2 噪声章节过滤

以下章节对 RAG 检索无实质贡献，解析时跳过：

| 跳过类别 | 典型章节标题 |
|---------|------------|
| 参考文献 | References |
| 致谢 | Acknowledgements |
| 利益声明 | Conflict of Interest, Competing Interests |
| 资金来源 | Funding |
| 作者贡献 | Author Contributions |
| 补充材料 | Supplementary Material, Appendix |
| 缩略词表 | Abbreviations |

### 2.3 四策略切分体系

```
输入文献
  ├─ 摘要（Abstract）
  │    ├─ ≤ 512 tokens（91%+）→ 【策略 A】整体入库
  │    └─ > 512 tokens（<9%） → 【策略 B】Recursive 滑动窗口
  │
  └─ 正文（Body）
       ├─ 同章节段落合并 ≤ 512 tokens → 【策略 C】段落合并块
       └─ 合并后仍 > 512 tokens       → 【策略 D】Recursive 二级切割
```

| 策略 | 触发条件 | 处理方式 |
|------|---------|---------|
| **A** 摘要整体 | 标题+摘要 ≤ 512 tokens | 直接入库，chunk_id = pmc_id |
| **B** 摘要滑动 | 标题+摘要 > 512 tokens | `RecursiveCharacterTextSplitter(chunk_size=400, chunk_overlap=80)` |
| **C** 正文合并 | 合并后 ≤ 512 tokens | 同 section 内段落滚动合并，目标 ~300 tokens/组 |
| **D** 正文递归 | 合并后 > 512 tokens | 对合并文本再做 Recursive 切割 |

### 2.4 段落合并算法（策略 C）

同一 `section_path` 下的段落按顺序滚动累积，当累积 token 数达到 `merge_target=300` 时新开一组。合并优于逐段入库的原因：

- 单段落往往过短（中位数约 150 tokens），独立检索时语义不完整
- 合并至 ~300 tokens 保留局部上下文，同时大量缓冲在 512 上限以内
- 实测 p95 为 427 tokens，无一超限（见第三节）

### 2.5 Chunk 文本格式

所有 body chunk 以章节标题开头，格式固定：

```
{section_title}

{merged_paragraph_text}
```

例：
```
Statistical Analysis

Continuous variables were compared using Student's t-test or Mann–Whitney U test,
as appropriate. Categorical variables were compared using the chi-square test or
Fisher's exact test. A two-sided p-value < 0.05 was considered statistically
significant. All analyses were performed using SPSS version 26.0.
```

标题前缀使 chunk 在脱离文档上下文后仍能被正确归类，支持按 IMRaD 维度过滤检索。

### 2.6 IMRaD 自动分类

每个 body chunk 均被归类为以下 IMRaD 类型，供检索过滤使用：

| 类型 | 关键词（小写，含即命中） |
|------|------------------------|
| `introduction` | introduction, background, objective, aim, rationale |
| `methods` | method, material, patient, cohort, procedure, protocol, statistical, experiment |
| `results` | result, finding, outcome, observation |
| `discussion` | discussion, conclusion, interpretation, implication, limitation |
| `other` | 其余章节（Case Report / Data / Supplementary 等） |

## 三、实验结果

> 测试规模：前 50 篇文献（Smoke Test），处理时间 9.5 秒

### 3.1 整体产出

| 指标 | 值 |
|------|----|
| 输入文献 | 50 篇 |
| 成功解析 | 49 篇（1 篇因文章类型过滤） |
| 摘要 chunks | 49 |
| 正文 chunks | 908 |
| **合计 chunks** | **957** |
| chunks / 篇均值 | 19.5 |
| 处理速度 | ~5 篇/秒 |

相比摘要模式（每篇约 1 个 chunk），全文模式将每篇文献的可检索单元扩展了约 **19.5 倍**。

### 3.2 策略分布

| 策略 | Chunks 数 | 占比 |
|------|----------|------|
| A — 摘要整体 | 49 | 5.1% |
| C — 正文段落合并 | 834 | 87.2% |
| D — 正文递归切割 | 74 | 7.7% |
| **合计** | **957** | 100% |

策略 B（摘要 Recursive 切）未触发，说明本批 50 篇文献摘要全部在 512 tokens 以内。策略 D 占 7.7%，与实测段落超限比率（4.8%）接近，小幅偏高源于合并后少数段落组跨越上限。

### 3.3 Token 分布

| 统计量 | 值 |
|--------|----|
| 均值 | 248.4 |
| 中位数 | 242.0 |
| p90 | 388.0 |
| p95 | 427.0 |
| p99 | 482.9 |
| 最大值 | **512** |
| 最小值 | 22 |
| **超 512 限制** | **0 块（0.0%）** |


分布集中在 100–400 tokens 区间，峰值在 200–299 区间，形态健康，嵌入利用率高。唯一的 512 token 块恰好踩到上限（策略 C 的判定条件是 ≤ 512），不计超限。

### 3.4 质量验证（抽样 100 块）

| 检查项 | 结果 |
|--------|------|
| 超模型 Token 上限 | **0 块（0%）** ✅ |
| 含章节/标题前缀 | **100%** ✅ |
| 空文本 | **0 块** ✅ |
| 疑似末尾截断 | **0 块（0%）** ✅ |

### 3.5 IMRaD 分布

| IMRaD 类型 | Chunks | 占比 |
|-----------|--------|------|
| results | 358 | 37.4% |
| other | 211 | 22.1% |
| methods | 131 | 13.7% |
| discussion | 125 | 13.1% |
| introduction | 83 | 8.7% |
| abstract | 49 | 5.1% |

Results 占比最高（37.4%），符合医学论文以数据汇报为主的特征。分布合理，无明显偏斜，IMRaD 标签可用于检索时按章节维度过滤。

## 四、输出 Schema

每条 chunk 包含以下字段：

### 核心内容字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `chunk_id` | str | 唯一标识（摘要：pmc_id；正文：pmc_id_body_00000） |
| `text` | str | 入库文本，格式："章节标题\n\n内容" |
| `doc_id` | str | 所属文献 pmc_id |
| `chunk_index` | int | 当前文档内编号 |
| `total_chunks` | int | 当前文档 chunk 总数 |
| `source_title` | str | 原文标题 |
| `token_count` | int | 精确 token 数（tiktoken） |

### 结构语义字段（新增）

| 字段 | 类型 | 示例值 |
|------|------|--------|
| `chunk_type` | str | `"abstract"` / `"body"` |
| `section_title` | str | `"Statistical Analysis"` |
| `section_path` | str | `"Methods > Statistical Analysis"` |
| `imrad_type` | str | `"methods"` |
| `split_strategy` | str | `"C_body_merged"` |

### 文献元数据字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `pmc_id` | str | PMC 唯一标识 |
| `pmid` | str | PubMed ID（约 73% 有值） |
| `doi` | str | DOI（约 95% 有值） |
| `journal` | str | 期刊名（标准化） |
| `pub_year` | int | 发表年份 |
| `article_type` | str | 文章类型 |
| `abstract_source` | str | `"original"` / `"body_fallback"` |
| `source_url` | str | 溯源 URL（三级兜底，100% 覆盖） |

## 五、运行方式

### 5.1 全文模式

```powershell
# Windows 控制台需设置 UTF-8
$env:PYTHONUTF8="1"

# 全文模式（摘要 + 正文）
python pmc_document_splitter.py --split full --fulltext

# 测试（限制文献数）
python pmc_document_splitter.py --split ft_test --limit 500 --fulltext

# 调整段落合并目标（默认 300 tokens）
python pmc_document_splitter.py --split full --fulltext --merge-target 250
```

### 5.2 仅摘要模式（兼容原有行为）

```powershell
python pmc_document_splitter.py --split abstract_full
```

### 5.3 关键参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--fulltext` | 关 | 启用正文切分 |
| `--merge-target` | 300 | 同 section 段落合并目标 token 数 |
| `--chunk-size` | 400 | Recursive 切割块大小（B/D 策略） |
| `--chunk-overlap` | 80 | Recursive 重叠 token 数（B/D 策略） |
| `--embed-limit` | 512 | 嵌入模型 Token 上限 |
| `--limit` | 全量 | 限制处理文献数（测试用） |

## 六、设计权衡与局限

### 6.1 未采用的方案

| 方案 | 未采用原因 |
|------|----------|
| 整个 `<sec>` 作为分块单元 | 37.9% leaf-sec 超 512 tokens，仍需大量二次切割 |
| 语义切分（sentence-transformers） | 速度慢，投入产出比低；JATS 结构已提供足够语义边界 |
| Late Chunking（bge-m3） | 需要更换嵌入模型，作为后续优化项保留 |
| 跨章节合并 | 会混淆 IMRaD 语义边界，降低过滤精度 |

### 6.2 已知局限

- **表格数值**：表格内数值仅通过 `<caption>` 进入索引，表格主体数据未入库
- **公式**：数学公式（`<inline-formula>`）在 itertext() 提取时可能变为空白
- **极短 chunk**：最小 22 tokens，部分来自图表标注，检索时噪声略高

### 6.3 后续优化方向

1. **Small-to-big 检索**：以 body chunk 做相似度匹配，返回时附带所在 `<sec>` 全文作为上下文
2. **表格结构化入库**：解析 `<table>` 标签，将数值以"列名: 数值"格式转为文本块
3. **Late Chunking**（bge-m3）：对特别长的章节使用晚期分块，保留跨段的长程上下文

## 七、总结

| 维度 | 指标 |
|------|------|
| 正文分块单元 | 同章节段落合并（merge_target=300 tokens） |
| 无超限块 | 0 / 957（0.0%）|
| 质量合格率 | 100%（含前缀、无空文本、无截断） |
| 每篇 chunks 均值 | 19.5（vs. 摘要模式 ~1.09） |
| 策略主力 | 策略 C（段落合并，87.2%）|
| 新增字段 | chunk_type / section_title / section_path / imrad_type |

全文模式相比摘要模式将每篇文献的可检索粒度扩展约 **18 倍**，在保证 0% 超限、100% 质量合格的前提下，使 RAG 系统具备回答方法细节与具体数值类问题的能力。
